Database setup – manual first start

Step by step: create a new, empty database, create the schema, create the user accounts with passwords, and prepare the app for its first use. Takes about 15–20 minutes and is done once by an administrator.

  • Step 1 – Create the Supabase project
  • Step 2 – Create the schema (migrations)
  • Step 3 – Check the schema
  • Step 4 – Switch off self-registration
  • Step 5 – Create user accounts and passwords
  • Step 6 – Names and colours
  • Step 7 – Copy URL and key
  • Step 8 – First login, cars and split rule
  • Later administration (passwords, new and leaving members)
  • Backup

Step 1 – Create the Supabase project

  1. Register for free at supabase.com and sign in.
  2. New project: choose a name (e.g. carsharing), a strong database password (store it safely — it is the PostgreSQL superuser password, not a family login), and the region Frankfurt (eu-central-1), the closest one for Germany.
  3. Wait until the project is ready (about two minutes).

Step 2 – Create the schema (migrations)

The scripts are in the folder supabase/migrations/ of the source code. Run them one after another, in this order:

  1. In the Supabase dashboard open SQL Editor → New query.
  2. Open 0001_init.sql in a text editor, copy the entire content, paste it into the SQL Editor and click Run. The result must say Success.
  3. Repeat with a new query for each further script: 0002_booking_reference.sql, 0003_shared_trips.sql, 0004_settlement_payments.sql, 0005_profile_update_columns.sql, 0006_car_drive_type.sql, 0007_harden_cars_and_quantities.sql, 0008_profile_colors.sql.
Notes
  • Never skip a script and never change the order; each one builds on the previous ones.
  • 0007 and 0008 end with a check query; every row should show ok.
  • If a script fails, read the error message, fix the cause and run the same script again before continuing.
  • When updating an existing installation later, run only the scripts that are new.

Step 3 – Check the schema

Run in the SQL Editor:

select table_name
from information_schema.tables
where table_schema = 'public'
order by table_name;

Expected: bookings, cars, expenses, profiles, settings, settlement_payments, trips.

-- exactly one settings row with the default rule
select * from public.settings;

-- the trigger that creates profiles for new accounts
select tgname from pg_trigger where tgname = 'on_auth_user_created';

Step 4 – Switch off self-registration

Authentication → Sign In / Providers → Email: switch off Allow new users to sign up and save. Otherwise strangers who know the address could create an account themselves. (The Email provider itself stays enabled — it is used for logging in.)

Do this before the app is published. Every new account automatically becomes an active family member with full access.

Step 5 – Create user accounts and passwords

Each family member needs their own account. For every person:

  1. Open Authentication → Users → Add user → Create new user.
  2. Enter the person's e-mail address (it is the login name) and a password.
  3. Tick Auto Confirm User, so no confirmation e-mail is needed.
  4. Click Create user.

The trigger handle_new_user immediately creates a matching row in public.profiles: display name = the part of the e-mail address before the @, colour = blue, active = yes.

Passwords
  • Use an individual password per person, at least 8 characters (Supabase's minimum is 6; a stricter minimum can be set under Authentication → Providers → Email / password settings).
  • Give each person their password personally (not in a family group chat). The app has no "change password" function; see Change or reset a password.
  • A password manager or the phone's keychain can store the login; the login form supports autofill.

Check that every account has a profile:

select u.email, p.display_name, p.color, p.active
from auth.users u
left join public.profiles p on p.id = u.id
order by u.created_at;

Step 6 – Names and colours

Each person can set their display name and calendar colour themselves in the app under „Mehr → Mein Profil“. As administrator you can also set them in advance, so the family sees proper names and different colours from the start:

update public.profiles set display_name = 'Anna',  color = '#2a78d6'
where id = (select id from auth.users where email = 'anna@example.com');

update public.profiles set display_name = 'Ben',   color = '#d95926'
where id = (select id from auth.users where email = 'ben@example.com');

Step 7 – Copy URL and key

Under Project Settings → API (in newer dashboards also Project Settings → Data API / API Keys) copy the Project URL and the anon public key. They go into .env.local and into the GitHub secrets — see Installation, step 4.

Never use the service_role (secret) key in the app or in GitHub secrets for the app. It bypasses all security rules.

Step 8 – First login, cars and split rule

  1. Open the app (locally with npm run dev or the published address) and sign in with one of the accounts.
  2. „Mehr“ → section „Autos“ → „Auto hinzufügen“: enter each car with name, licence plate, drive type and the current odometer reading („km-Stand jetzt“). All kilometres are counted from this reading.
  3. Under „Kostenverteilung“ choose how costs are shared (default: Fixkosten gleich, Verbrauch nach km).
  4. Optional: enter the current yearly bills (insurance, tax) under „Kosten“ with „Über einen Zeitraum verteilen“.
  5. Tell the family the address and their login; they continue with the user guide.

Later administration

Add a new family member

Exactly as in Step 5. Self-registration stays switched off.

Change or reset a password

Option A – recovery e-mail: Authentication → Users, open the user's menu (⋯) → Send password recovery. The person receives an e-mail with a link. For the link to lead back to the app, set the app address under Authentication → URL Configuration → Site URL (e.g. https://<user>.github.io/CarSharingApp/).

Option B – set a new password directly (administrator, in the SQL Editor):

update auth.users
set encrypted_password = extensions.crypt('New-Secret-Password', extensions.gen_salt('bf')),
    updated_at = now()
where email = 'anna@example.com';

Option B writes into Supabase's internal auth table. It works with the standard Supabase setup (bcrypt hashes, pgcrypto in schema extensions); prefer option A when e-mail works. Tell the person the new password personally.

A member leaves – deactivate instead of delete

Deactivating keeps all their trips, costs and payments in past settlements, but they can no longer read or change anything. Members cannot re-activate themselves.

update public.profiles set active = false
where id = (select id from auth.users where email = 'ben@example.com');

Re-activate with active = true. Optionally also block the login under Authentication → Users (ban user) or change the password.

Deleting a user in Authentication → Users also deletes their profile and, with it, their reservations, the costs they paid and their settlement payments. Past settlements would change. Deactivate instead.

Change the login e-mail

Authentication → Users → open the user → change the e-mail address. The profile stays linked.

Backup

  • Supabase makes daily backups on paid plans; on the free plan export regularly yourself, e.g. Table Editor → table → Export to CSV for each table, or with pg_dump using the connection string from Project Settings → Database.
  • The CSV export of the settlement in the app is a convenient monthly record for the family.
  • Free Supabase projects are paused after a longer period without any use; they can be resumed in the dashboard.
