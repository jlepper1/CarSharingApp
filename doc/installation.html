Installation on a new environment

How to set up the source code on a new computer, run it locally, and publish it so the family can use it.

1. Prerequisites

WhatVersion / note
Node.js with npmVersion 22 (the same as the build pipeline). Check with node -v.
GitAny current version
Supabase accountFree at supabase.com — hosts the database and logins
GitHub accountHosts the source code and the published app (GitHub Pages)
Editor (optional)Visual Studio Code; the repository contains CarSharingApp.code-workspace

2. Database

A Supabase project with the schema and user accounts must exist first. Follow Database setup, then continue here with the Project URL and the anon public key.

3. Get the code and install dependencies

git clone https://github.com/<user>/CarSharingApp.git
cd CarSharingApp
npm install

npm install downloads all libraries listed in package.json into node_modules/. For an exact, reproducible install (as in the pipeline) use npm ci.

4. Configure the connection

Copy .env.example to .env.local in the project folder and fill in the values from the Supabase dashboard (Project Settings → API):

VITE_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOi...
VITE_DATA_PROVIDER=supabase
  • .env.local is ignored by Git and is not committed.
  • The anon key is public by design; the data is protected by the database's row level security.
  • Never use the service_role key here — it bypasses all security rules.
  • If the values are missing, the app shows the screen „Einrichtung nötig“ instead of the login.

5. Run, test and build locally

CommandWhat it does
npm run devStarts the Vite development server on http://localhost:5173. It is also reachable in the home network (e.g. http://192.168.x.x:5173, printed in the console), so it can be opened on a phone.
npm testRuns all unit and screen tests once (npm run test:watch keeps watching).
npm run lintStatic code checks with oxlint.
npm run buildType check and production build into dist/.
npm run previewServes the built dist/ folder locally to try the production build.

6. Publish on GitHub Pages

The workflow .github/workflows/deploy.yml runs on every push to main (or manually via Run workflow): npm ci → npm test → npm run build → publish dist/ to GitHub Pages. One-time setup in the GitHub repository:

  1. Push the code to a GitHub repository named CarSharingApp.
  2. Settings → Pages → Source: select GitHub Actions.
  3. Settings → Secrets and variables → Actions → New repository secret: create VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY with the same values as in .env.local.
  4. Push to main (or start the workflow manually under Actions).
  5. After a minute or two the app is available at https://<user>.github.io/CarSharingApp/.

The workflow builds with VITE_BASE=/CarSharingApp/ because GitHub Pages serves the app from that sub-path. If the repository has a different name, change VITE_BASE in the workflow accordingly.

7. Other web servers

The built app is just static files. To host it elsewhere:

# build for a server where the app lives at the root path "/"
npm run build
# or for a sub-path, e.g. https://example.com/carsharing/
VITE_BASE=/carsharing/ npm run build

Copy the content of dist/ to the web server. Use HTTPS — it is required for the service worker and for installing the app on phones. The VITE_SUPABASE_* variables must be set (via .env.local or the environment) at build time; they are compiled into the JavaScript.

8. Install the app on phones

  • iPhone / iPad: open the address in Safari (not Chrome), tap Teilen (share) → Zum Home-Bildschirm.
  • Android: open the address in Chrome, menu ⋮ → App installieren.
  • Desktop: works in any current browser; Chrome and Edge also offer to install it as an app.

The installed app updates itself automatically when a new version is published.

9. Updating to a new version

  1. If the new version contains new files in supabase/migrations/, run only the new ones, in order, in the Supabase SQL Editor — before pushing, because a push deploys immediately.
  2. git pull, npm install, npm test.
  3. Push to main; GitHub Actions builds and publishes.
  4. Releases are marked with a commit „Release version X.Y.Z“ (version in package.json) and a Git tag vX.Y.Z. The running version is shown at the bottom of the „Mehr“ screen.
