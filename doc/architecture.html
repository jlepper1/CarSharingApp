Programming language and libraries

The app is written in TypeScript (version 6, strict type checking). The database logic — constraints, triggers, security policies — is written in SQL / PL/pgSQL for PostgreSQL.

Application server and hosting

The app has no application server of its own. It is a single-page application: the build produces static HTML, JavaScript and CSS files, and all logic runs in the browser. Data access and business rules that must be guaranteed live in the database.

  • Web hosting: GitHub Pages serves the static files at https://<user>.github.io/CarSharingApp/. GitHub Actions (.github/workflows/deploy.yml) runs the tests, builds and publishes on every push to main. Any static web server (nginx, Apache, Netlify, …) would work as well.
  • Backend: Supabase (hosted, free tier is sufficient). It provides
    • PostgreSQL — the database,
    • Supabase Auth (GoTrue) — e-mail/password login and session tokens (JWT),
    • PostgREST — the REST API that the app uses to read and write tables and call functions,
    • Realtime — pushes table changes to all open apps (live reload),
    • Storage — a private receipts bucket (prepared for receipt photos).
  • Development: the Vite development server (npm run dev, port 5173) serves the app locally and in the home network, so it can be tested on a phone.

Data access seam: no screen talks to Supabase directly. Everything goes through the DataProvider interface. This keeps the screens testable with a mocked provider and would allow another backend by writing one new provider class. Supabase is the chosen backend permanently, so the database is free to use PostgreSQL-specific features.

Database design

The database is the single source of truth and enforces the rules that must never be broken, so they hold even if two phones save simultaneously or someone bypasses the app and calls the API directly. The app's own checks are only for friendly error messages.

Tables (schema public)

TableContentImportant columns and rules
profilesOne row per family member, linked 1:1 to the login account auth.usersdisplay_name, color, active. Created automatically when an account is added.

tripsDriven tripscar_id, participant_ids (array of profiles, at least one), driven_on, odometer_start, odometer_end, generated distance_km. Exclusion constraint: no overlapping odometer ranges per car.
expensesCostsuser_id (who paid), category (enum), amount_cents (integer), incurred_on, optional period_start/period_end, liters (fuel only), kwh (charging only), car_id (optional).
settlement_paymentsTransfers marked as paidfrom_user, to_user, amount_cents > 0, applies_on (last day of the settled period).
settingsExactly one row (id = 1)split_rule (enum), currency.

Bookings, trips and expenses also carry the audit columns created_by, updated_by, updated_at, which are set by a trigger — never by the app.

Rules enforced by the database

  • No double booking: exclude using gist (car_id with =, tstzrange(starts_at, ends_at) with &&) (extension btree_gist).
  • No double-counted kilometres: the same kind of exclusion constraint on the odometer range of trips per car.
  • Derived distance: distance_km is a generated column (odometer_end - odometer_start), so it can never disagree with the readings.
  • Money in cents: amount_cents integer; no floating-point money anywhere.
  • Consistency checks: end after start, odometer end ≥ start, period start and end both set or both empty, litres only for fuel, kWh only for charging, quantities > 0.
  • Inactive cars: trigger check_car_active rejects new bookings and trips for a deactivated car.
  • Valid participants: trigger check_trip_participants accepts only existing family members.

How the app reads data

  • Screens ask the DataProvider for a date range (e.g. the month shown). The Supabase provider issues PostgREST queries with filters and maps rows to domain types.
  • The settlement is calculated in the browser from the trips, expenses and payments of the period (src/lib/settlement.ts). Nothing derived is stored, so a correction to an old trip immediately changes the settlement.
  • All tables are added to the supabase_realtime publication. The app subscribes to changes (src/lib/useLiveReload.ts) and quietly reloads; bursts of changes trigger one reload.

Security model

  • Authentication: e-mail and password via Supabase Auth. Self sign-up is switched off; the administrator creates every account.
  • Row level security (RLS) is enabled on every table. Every policy requires is_family_member(): only signed-in, active members can read or write anything. Anonymous requests see nothing.
  • Trust model: every active member may create, change and delete every booking, trip and expense. The audit columns show who did what.
  • Profiles: a member may change only their own display_name and color. The active flag can only be changed in the Supabase dashboard, so a deactivated member cannot re-enable themselves.
  • Cars cannot be deleted by anybody through the API.
  • The anon key in the app is public by design; the RLS policies protect the data. The service_role key must never be put into the app.

Migrations

The schema is created and changed only by the numbered SQL scripts in supabase/migrations/, run in order in the Supabase SQL Editor. The scripts use if not exists / drop … if exists so that running one twice does no harm; still, run each script only once.

Settlement calculation

  1. Collect the costs of the period. A cost with a period (yearly bill) contributes only the days that fall into the settled period.
  2. Split each cost by the chosen rule: equally between the involved members (all active members, plus inactive ones who still drove or paid in the period), or by each member's share of the kilometres (a shared trip counts once and its km are split equally between its participants).
  3. Everything is in whole cents; leftover cents go to the largest remainders, so shares add up exactly.
  4. Balance per person = paid − share ± settlement payments.
  5. Transfers: repeatedly match the largest debtor with the largest creditor, giving few, simple payments.

Tests and quality

  • npm test runs Vitest: settlement maths, dates, formatting, CSV and PDF export, the Supabase provider mapping, and screen tests with a mocked provider.
  • The GitHub Actions workflow runs the tests before every deployment; a failing test stops the deployment.
  • npm run lint (oxlint) and tsc (part of npm run build) check code quality and types.
